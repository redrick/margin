margin

Review git changes in the terminal with a coding agent beside you, writing in the margin of every change.

go install github.com/redrick/margin/cmd/margin@latest
read the README →

needs go 1.24+, git and tmux · agent defaults to claude, any CLI agent via $MARGIN_AGENT

01Run it where the change is

Inside any repository, margin opens the changed code next to a fresh agent. The diff is drawn in the gutter; the agent's comments sit beside each change as it writes them. Press a on a line to ask about it, ask for a fix in the agent's pane, and watch the answer land in the review.

1Not only on problems. The agent is asked to annotate every changed block: why it is there and whether it looks right.
margin              # review uncommitted changes
margin --staged     # review only what is staged
margin feature-x    # a branch against the main branch
margin a1b2c3d      # one commit
margin --pr 123     # a GitHub pull request, read-only

The review and the agent share a private tmux server attached to a single pane. Run margin again and it reattaches where you left off, with your verdicts, marks and comments intact.

2In plain tmux it splits the current pane; outside tmux it takes over the terminal. Inside gw, a sub-window of the worktree.

02Three phases, always in order

margin walks you through the review one step at a time. The top line always says where you are.

spacego onnext step, next stop
bgo backprevious step
ccommentissue, suggestion, question…
aaskthe agent, about this line
①

Orient

One screen, one question. What the change is for, what it does, the gap between them, and the route through it. Then, before any code: does this change make sense, done this way? y ? n

②

Walk

Each stop opens with a card: what it is, its risk, why now, the one thing to check. Then one reading unit per step, the agent's notes numbered beside their lines, and a question to answer before space. Import edits wait together at the end. A verdict closes the stop: 1 2 3

③

Decide

The recap turns your verdicts into a recommendation — approve, request changes, or not finished — and lists exactly what is left. margin export prints it ready to paste. margin never posts on its own.

03Around the edges

Which changed lines does no test run?

The agent measures coverage per test. Untested lines are marked in the gutter; u jumps between them, t lists the tests that run a line.

Comments the author can act on

c first asks what kind of comment it is, after Conventional Comments, then tells you what a good one of that kind contains while you type.

Ask about a line

The question is typed into the agent's pane; the answer comes back as a note anchored on that line.

Callers, examples, history

Around each stop: who calls the changed function, what the code did before and does now, and the commits that shaped it. enter peeks.

Moved code, recognised

Code that only moved is shown as moved, not as a deletion and an addition you have to compare by eye.

Export, never post

Markdown to paste into the pull request, or --format github for gh api with the matching event. You press send.

04Why it works this way

Every choice in the walk follows something the research on code review found.

  1. Orient first, then the main part, then the rest. Ask whether the change makes sense at all before any detail — the rest may not survive the answer.Google, navigating a CL
  2. Few, coarse steps rather than a long checklist. Strict step-by-step guidance helped on small changes but got in the way on large ones.Gonçalves et al., 2022
  3. The order is shown and explained. Reviewers prefer reading what is used before what uses it, so stops come in dependency order.Baum et al., 2017
  4. One change at a time, related changes together. Reviewers find more defects when the order follows the code's relations, not file names.Baum et al., 2019
  5. Risky parts early. What a reviewer reads last gets fewer comments.Fregnan et al., 2022
  6. A pause around 400 lines or 90 minutes. The footer tracks both, and margin resumes where you stopped.review quality drops past either

05Built for code you did not write

  • Read-onlymargin never writes to the repository and never executes anything from it. git only through read-only plumbing, refs after --end-of-options.
  • Rules from the base side.margin/ignore and .margin/instructions are read from the commit compared against, so a change cannot rewrite the rules it is reviewed by.
  • Clean terminalEscape sequences and bidi controls are stripped before rendering. Questions are never typed into a plain shell.
  • Untrusted text, markedCommit messages, PR descriptions and repository instructions reach the agent labelled as written by other people.

Read the change. Let the agent take notes.

The problem

A diff tells you what changed.
Not why, not where to start, not when you are done.

Changes arrive faster than ever, many of them written by agents. Skimming a wall of red and green is how bugs get approved. margin turns the wall into a route.

margin

  • A route, with reasonsRelated files grouped into a few stops, in dependency order, each saying why it comes where it does.
  • A note on every changeWhy it is there and whether it looks right, beside the line. Untested lines marked in the gutter.
  • Ask on the linePress a. The answer lands as a note right where you asked.
  • A verdict you can defendThe recap recommends approve or request changes, and lists exactly what is still open.
How it works

Three phases. Four keys.

space go on · b go back · c comment · a ask. Everything else can wait behind H.

①Orient

One screen, one question.

What the change is for, what it actually does, and the gap between the two. Then the route. Then, before a single line of code: does this make sense, done this way?

y walk it? not sure yetn say why, skip to decide
②Walk

Every stop opens with a card.

What it is, how risky, why it comes now, and the one thing to check. You know what you are looking for before you look.

②Walk

One change per step.

A whole reading unit, with the agent's notes numbered beside their lines and a question to answer before space. Import churn is batched at the end so it never interrupts.

②Walk

Settle it where it belongs.

Problems to agree with, calls to make, questions only the author can answer — listed right under the code they are about. Nothing piles up for the end.

②Walk

Comments the author can act on.

c asks the kind first — issue, suggestion, question, nitpick, praise, thought — and coaches you while you type. S sends them; the agent fixes the code or explains why not.

③Decide

The recap tells you what to do.

Approve, request changes, or not finished — with the reasons and every open item one enter away. margin export makes it a PR review you post yourself.

Everything around the change

The context you would have gone looking for.

Already on screen, one key away, without leaving the review.

Test coverage

See which changed lines no test runs.

The agent measures coverage per test. Untested lines glow in the gutter, u jumps between them, t lists the tests that run a line and spotlights one.

Start anywhere

One command.

margin            # uncommitted
margin --staged   # the index
margin feature-x  # a branch
margin a1b2c3d    # a commit
margin --pr 123   # a pull request
Around this stop

Callers, examples and history.

Who calls the function you are reading, what it did before and does now, and the commits that shaped it. enter peeks.

Spotlight

Follow one test through the change.

Pick a test and every line it does not run dims. See exactly which path it takes.

Moved code

Moved, not rewritten.

Code that only moved is shown as moved — not as a deletion and an addition you compare by eye.

Blind mode

Read first, then see the notes.

v hides the agent's notes on high-risk stops, so you form your own view before you see theirs.

Resume

Stop any time.

Run the same command tomorrow. Verdicts, marks, comments and notes are exactly where you left them.

Export

A review ready to post.

Markdown to paste, or --format github for gh api with the right event. margin never posts for you.

Per repository

Teach it your codebase.

.margin/ignore skips generated files. .margin/instructions tells every review what deserves care — read from the base commit, so a change cannot rewrite its own rules.

Not a hunch

Built on what code review research found.

Every part of the walk follows a published result about how people actually review code.

Ask "does this make sense?" before any detail.

Design comments come first; the details may not survive them.

Google, navigating a CL →
Few, coarse steps — not a checklist.

Strict step-by-step guidance helped on small changes but got in the way on large ones.

Gonçalves et al., 2022 →
Show the order, and explain it.

Reviewers prefer reading what is used before what uses it, and get lost in orders they cannot follow.

Baum et al., 2017 →
Related changes together.

More defects are found when the order follows the code's relations rather than file names.

Baum et al., 2019 →
Risky parts early.

Whatever a reviewer reads last gets fewer comments.

Fregnan et al., 2022 →
Comments with a kind.

Labelling each comment tells the author what is a request and what is a thought.

Conventional Comments →
read-only
Safe by design

Made for code you did not write.

margin treats the repository under review as untrusted. You can point it at a stranger's pull request.

  • Never writes, never runsNo writes to the repository, nothing executed from it. git only through read-only plumbing, refs after --end-of-options.
  • Rules from the base.margin/ settings come from the commit compared against, so a change cannot loosen its own review.
  • Clean terminalEscape sequences and bidi controls are stripped before rendering. Questions never go to a plain shell.
  • Untrusted text, labelledCommit messages, PR descriptions and repo instructions reach the agent marked as written by someone else.
